### สกุลเงินท้องถิ่น USDC และค่าใช้จ่ายจริง

- USDC อิงดอลลาร์สหรัฐ ไม่ใช่ค่าคงที่เมื่อคิดเป็นสกุลเงินท้องถิ่น ถ้าอัตรา USD/สกุลท้องถิ่นเปลี่ยน 5% (ตัวเลขสมมติเพื่อให้เห็นขนาด) งวดละ 100 USDC จะเปลี่ยนในรูปสกุลท้องถิ่น 5% คนที่มีรายได้เป็นสกุลท้องถิ่นรับความเสี่ยงนี้เอง ระบบแก้ไม่ได้
- ต้นทุนที่ผู้ใช้เจอจริง: spread/ค่าธรรมเนียมแปลงสกุลท้องถิ่น–USDC ขาเข้าและขาออก, gas ทุกครั้งที่จ่าย/เบิก, การมี USDC เหลือไว้เป็น gas, เงินมัดจำที่ล็อก (ต้นทุนค่าเสียโอกาส)
- ช่องทางแปลงสกุลท้องถิ่น–USDC ในเขตอำนาจเป้าหมายยังไม่ได้ยืนยัน (ส่วนที่ 1) ต้องกำหนดผู้ให้บริการที่ถูกต้องตามกฎหมายของเขตนั้นก่อนเปิดทดลองกับผู้ใช้จริง
- การกู้คืนกระเป๋า: ให้เลือกกระเป๋าที่ผู้ใช้เป็นผู้คุมกุญแจ (เช่นแบบ passkey) พร้อมกระบวนการกู้คืนที่ทดสอบแล้ว ถ้าผู้ให้บริการเป็นผู้ถือกุญแจแทน ต้องประเมินกฎหมายการรับฝาก/ดูแลสินทรัพย์ดิจิทัลก่อน
- การช่วยเหลือผู้ใช้ (customer support): กระบวนการข้อพิพาทและการช่วยกู้กระเป๋าเป็นงานนอกเชนที่ต้องมีคนรับผิดชอบ สัญญาทำแทนไม่ได้

### ความเป็นส่วนตัว

- ห้ามเก็บชื่อจริง เลขบัตร เอกสาร KYC เบอร์โทร หรือชื่อกลุ่มที่ระบุตัวบุคคลไว้บนเชนสาธารณะ รวมถึงใน memo (Arc มี Memo contract ที่เปิดเผย event สาธารณะ [F])
- เก็บบนเชนเฉพาะ: ที่อยู่กระเป๋า รหัสสมาชิกแบบสุ่ม ค่าสถานะยืนยันตัวตน (หรือค่าแฮช) และตัวเลขการเงิน
- เอกสาร KYC เก็บกับผู้ให้บริการนอกเชน ภายใต้กฎหมายคุ้มครองข้อมูลส่วนบุคคลของเขตอำนาจที่เกี่ยวข้อง (ภาระหน้าที่รายละเอียดยังไม่ได้ตรวจ)
- แจ้งผู้ใช้ตรง ๆ ว่ากระเป๋าและความสัมพันธ์ทางการเงินในกลุ่มมองเห็นได้สาธารณะ และเชื่อมโยงตัวตนจริงได้ถ้ามีคนรู้ว่ากระเป๋านั้นเป็นของใคร Arc มีแนวคิดสภาพแวดล้อมแบบ opt-in privacy ในเอกสาร แต่ไม่ได้ตรวจความพร้อมใช้งาน จึงไม่ถือเป็นทางแก้ใน MVP

## 2. กฎหมายและการสื่อสาร

### 2.1 ขอบเขต: ไม่วิเคราะห์กฎหมายไทย

ตามที่เจ้าของโครงการระบุ โครงการนี้ไม่ได้ดำเนินการในไทยและอยู่นอกกฎหมายไทย รอบก่อนผมวิเคราะห์ตามเงื่อนไข "หากเปิดในประเทศไทย" ที่โจทย์ตั้งไว้ ตอนนี้ถอนส่วนนั้นออกทั้งหมด (พ.ร.บ.การเล่นแชร์ พ.ร.ก.ฉ้อโกงประชาชน กฎสินทรัพย์ดิจิทัล และท่าทีของ ก.ล.ต./ธปท.) และไม่ใช้เป็นเกณฑ์ออกแบบอีก

สิ่งที่ **ไม่เปลี่ยน** เพราะไม่ได้ขึ้นกับกฎหมายประเทศใด:
- ความเสี่ยงทางการเงินและตัวเลขในส่วนที่ 2 (ผิดนัด หลักประกัน กองทุนสำรอง)
- ข้อเท็จจริงของ Arc/USDC ในส่วนที่ 1 (blocklist ของ USDC ยังบังคับตอนรันไทม์ [F])
- ข้อเสนอด้านสัญญา สิทธิผู้ดูแล และการไม่ให้ผู้ดูแลแตะเงินสมาชิก

### 2.2 "อยู่นอกกฎหมายไทย" ไม่เท่ากับ "ไม่มีกฎหมายใดบังคับ"

กฎหมายที่ใช้บังคับมักตามตัวบุคคลและกิจกรรมจริง ไม่ใช่ตามที่ตั้งของเครือข่ายบล็อกเชน อย่างน้อยต้องดูเขตอำนาจของ: (1) ผู้พัฒนา/ผู้ดำเนินการแพลตฟอร์มและผู้ถือสิทธิ multisig (2) ผู้จัดกลุ่ม (3) สมาชิกแต่ละคน (4) ผู้ให้บริการแปลงเงิน กระเป๋า และ KYC (5) ผู้ออก USDC ซึ่งบังคับ blocklist ได้ ผมไม่ทราบว่าเขตอำนาจเหล่านี้คือที่ใด จึง **ไม่ได้ตรวจกฎหมายใดในรอบนี้** และต้องเพิ่มเป็นคำถามที่ต้องตอบก่อนเปิดใช้เงินจริง

สิ่งที่ต้องให้ทนายในเขตอำนาจที่เกี่ยวข้องประเมิน (ไม่มีข้อสรุปจากผม):
1. วงออมหมุนเวียนแบบนี้มีข้อบังคับ ใบอนุญาต หรือข้อห้ามเฉพาะในเขตของสมาชิกหรือไม่ และใครถือเป็น "ผู้จัด"
2. การที่สัญญาถือ USDC ของสมาชิก (escrow) เข้าข่ายรับฝากเงิน บริการชำระเงิน หรือธุรกิจสินทรัพย์ดิจิทัลหรือไม่ และผู้ดูแลสัญญาเข้าข่ายตัวกลางหรือไม่
3. ค่าธรรมเนียมแพลตฟอร์มหรือกองทุนสำรองจะเข้าข่ายประโยชน์ตอบแทนหรือไม่
4. ภาระ AML/KYC และกฎการโอนข้อมูลผู้โอน (travel rule) ของผู้ให้บริการที่เกี่ยวข้อง
5. กฎคุ้มครองข้อมูลส่วนบุคคลสำหรับ KYC นอกเชนและข้อมูลที่โยงตัวตนกับกระเป๋า
6. กฎสินเชื่อ ดอกเบี้ย และใบอนุญาต (เฉพาะถ้าจะเปิด Microloan ในอนาคต)
7. การตลาดและการชักชวนสาธารณะ รวมถึงข้อห้ามเรื่องกองทุน/ผลตอบแทน
8. ผลเมื่อสมาชิกหลายเขตอำนาจอยู่ในกลุ่มเดียว และวิธีบังคับสิทธิข้ามประเทศเมื่อมีข้อพิพาท (ซึ่งยากและช้ากว่ากรณีในประเทศเดียว)

อย่าสรุปว่า: กลุ่มเล็กไม่ต้องตรวจกฎหมาย / ทำ KYC แล้วถูกกฎหมายทั้งหมด / ใช้ smart contract แล้วไม่มีผู้รับผิดชอบ / เปลี่ยนชื่อผลิตภัณฑ์แล้วหลุดจากข้อกำกับ / อยู่นอกประเทศหนึ่งแล้วไม่มีกฎหมายใดบังคับ

## 3. MVP

### 3.1 โมเดลที่เลือก: C-lite

**กลุ่มปิดรู้จักกัน ขนาดเล็ก คิวคงที่ มี holdback + มัดจำ + กองทุนสำรองเล็ก ไม่มี Microloan**

เหตุผล:
1. โมเดล A ปล่อยความเสียหายเต็ม 900/9 คน ผู้ใช้เปราะบางเสียหนัก โดยไม่มีข้อมูลผิดนัดจริงให้ปรับเทียบ
2. โมเดล B ให้สภาพคล่องเกือบศูนย์สำหรับคิวต้นรอบ จึงไม่ตอบ "ผู้ใช้เข้าไม่ถึงธนาคาร" และไม่มีข้อมูลใหม่ให้เรียนรู้
3. โมเดล D ทำให้ความเสี่ยงไปอยู่ที่ผู้ค้ำ (ถ้าผู้ค้ำไม่จ่ายก็ขาดทุนเต็ม) บังคับตามสัญญาได้ยาก และเพิ่มความซับซ้อนนอกเชน
4. C-lite ให้สภาพคล่องบางส่วน (คิว 1 รับสด 550 จาก 1,000) ลดความเสียหายต่อสมาชิกที่เหลือ และสร้างข้อมูลพฤติกรรมให้เรียนรู้

ข้อเสียที่ยอมรับ:
- ยังขาดทุนได้ (ตัวอย่าง 350 ใน 900 เมื่อคิว 1 หนี) จึงต้องบอกผู้ใช้ตรง ๆ
- ผู้ใช้ต้องมีเงินมัดจำ 100 ก่อนเริ่ม ซึ่งอาจเกินความสามารถของผู้มีรายได้น้อยที่สุด
- คิวท้ายต้องวางเงินสูงสุด (รวมมัดจำ 1,000) และรับความเสี่ยงเจ้าหนี้มากที่สุด
- ไม่ช่วยคนที่ไม่มีเงินออมเลย: ผลิตภัณฑ์นี้เป็นเครื่องมือออมอย่างมีวินัย ไม่ใช่เครดิต

| กลุ่ม 4 ถึง 10 คน คิวคงที่ ตกลงล่วงหน้า (ไม่สุ่ม ไม่ประมูล) | Reputation registry และการลด holdback ตามประวัติ | นำเงิน ROSCA ไปปล่อยกู้หรือหาผลตอบแทน |
| ชำระเอง + allowance จำกัดวงเงิน + ใครก็เรียกเก็บได้ | Microloan และกองทุนสินเชื่อ | สุ่มคิวด้วย `prevrandao`/block hash (Arc คืน 0 [F]) |
| holdback + มัดจำ + กองทุนสำรอง + น้ำตกตามกติกา | Governance และการโหวต | สัญญา upgradeable ที่ผู้ดูแลเปลี่ยนโค้ดได้ |
| ช่วงผ่อนผัน ผิดนัดโดยการประกาศ ปิดกลุ่มแบบหักกลบ | ผู้ค้ำประกันบุคคลธรรมดา | ค่าธรรมเนียมแพลตฟอร์มที่ยังไม่ผ่านการตรวจกฎหมาย |
| จ่ายก้อนแบบ pull (กัน blocklist) | Paymaster/gas ฟรีแบบเต็มรูปแบบ | เปิดรับสมาชิกสาธารณะ/โฆษณา |
| บัตรสรุปความเสี่ยง + แบบทดสอบความเข้าใจ | หลายกลุ่มต่อคนพร้อมกัน (วงเงินรวม) | ใช้การตลาดแบบ "ปลอดภัย 100%" |
| Wallet แบบผู้ใช้คุมกุญแจ + กระบวนการย้ายกระเป๋า | การสุ่มคิวด้วย oracle/VRF (ยังไม่ยืนยันบน Arc) | เก็บข้อมูลส่วนบุคคลบนเชน |
| ตัวทำดัชนีกับบอทเรียก `collect`/`declareDefault` | | ให้ผู้ดูแลมีสิทธิแตะเงินสมาชิก |

### 3.3 การทดลองก่อนเงินจริง

| ระยะ | ทำอะไร | เกณฑ์ผ่านก่อนไประยะถัดไป |
|---|---|---|
| 0 จำลองบนกระดาษ/สคริปต์ | จำลอง Monte Carlo: ผิดนัดแบบมีความสัมพันธ์กัน, ผิดนัดไม่พร้อมกัน, ผิดนัดบางส่วน; หาค่า φ, D, ρ, เพดานกองทุน, เกณฑ์ปิดกลุ่ม | ได้การแจกแจงความเสียหายรายคน และเจ้าของโครงการเซ็นรับเพดานความเสียหายที่ยอมรับได้ (คำถามข้อ 2) |
| 1 testnet ด้วยเงินจำลอง | สัญญาจริง กลุ่มทดลองเป็นทีมงานและกลุ่มเพื่อนที่เข้าใจว่าเป็นของจำลอง USDC บน testnet ไม่มีมูลค่า | ผ่านการทดสอบด้านล่างทั้งหมด |
| 2 ตรวจสอบอิสระ | ตรวจความปลอดภัยสัญญาโดยผู้ตรวจภายนอก + ความเห็นกฎหมายเป็นลายลักษณ์อักษร | ไม่มีข้อบกพร่องระดับสูง/วิกฤตที่ยังไม่แก้ และคำถามกฎหมายข้อ 1–4 ในส่วน 2.2 มีคำตอบจากทนายในเขตอำนาจที่เกี่ยวข้อง |
| 3 นำร่องเงินจริงขนาดเล็ก | กลุ่มปิดที่รู้จักกัน วงเงินกลุ่มต่ำกว่าเพดานที่เจ้าของโครงการกำหนดจากข้อ 0 | อยู่นอกขอบเขตของ Arc Studio: การใช้งานบน mainnet ต้องตรวจสอบ ทดสอบ และดำเนินการโดยผู้พัฒนาเองนอก Arc Studio |

### 3.4 การทดสอบที่ต้องทำ (ระยะ 1)

- **เศรษฐศาสตร์**: ผลน้ำตกตรงกับตารางส่วนที่ 2 ทุกกรณี และผลรวมไม่นับซ้ำ (ผลรวมถังเท่ากับเงินจริง)
- **Invariant/Fuzz** ตามหัวข้อ 6.3 ส่วนที่ 3 รันจำนวนครั้งมากพอที่ลำดับคำสั่งสุ่มยาวครอบคลุมหลายรอบ (จำนวนครั้งเป็นการตัดสินใจวิศวกรรม ตั้งต้น 10,000 ลำดับ [A] เพิ่มจนผลไม่เปลี่ยน)
- **โจมตี**: ผู้สร้างจัดคิว, หลายกระเป๋าในกลุ่มเดียว, ส่งเงินจิ๋วเพื่อทำให้ดูไม่ผิดนัด, front-run ระหว่าง `pay` กับ `declareDefault`, reentrancy ผ่านโทเคนที่ตอบกลับ, griefing ด้วยการหยุดฉุกเฉิน
- **USDC โอนไม่ได้**: จำลอง blocklist ที่ผู้รับ ผู้จ่าย และตัวสัญญา โดยใช้ Arc Foundry หรือ testnet เพราะ anvil มาตรฐานไม่จำลอง blocklist ของ Arc [F]
- **ระบบอัตโนมัติล่ม**: ไม่มีบอท 14 วัน (ตัวเลขสมมติ) ต้องไม่มีใครผิดนัดโดยไม่ได้ตั้งใจ และใครก็เรียกได้ทำงานต่อ
- **การย้ายกระเป๋า** ไม่ล้างหนี้ ไม่ย้ายสิทธิรับก้อนผิดคน
- **UX**: ผู้ใช้ทดลองตอบแบบทดสอบ 5 ข้อได้ถูกก่อนเข้าร่วม ถ้ามีข้อใดที่คนส่วนมากตอบผิด แสดงว่าบัตรสรุปไม่ชัด

### 3.5 ตัวชี้วัดและเงื่อนไขหยุด

ตัวเลขเกณฑ์ **ไม่กำหนดลอย ๆ** ทุกค่าด้านล่างมาจากข้อ 0 (Monte Carlo) และเพดานความเสียหายที่เจ้าของโครงการตกลง

| ตัวชี้วัด | อ่านเพื่ออะไร |
|---|---|
| สัดส่วนงวดที่จ่ายตรงเวลา / ในช่วงผ่อนผัน / ใช้มัดจำ / ผิดนัด | ปรับเทียบ G, R, D |
| ความสูญเสียจริงเทียบกับที่แบบจำลองคาด | แบบจำลองยังใช้ได้หรือไม่ |
| สัดส่วนผู้ตอบแบบทดสอบความเข้าใจถูกในครั้งแรก | บัตรสรุปชัดหรือไม่ |
| สัดส่วนธุรกรรมเรียกเก็บโดยคนอื่นที่ไม่ใช่บอท | พึ่งบอทเราเกินไปหรือไม่ |
| จำนวนครั้งที่ผู้ใช้ต้องการความช่วยเหลือ ต่อกลุ่ม | ภาระ customer support |

**หยุดทดลองทันทีเมื่อ**: (ก) invariant ใดผิด หรือยอดเงินในสัญญาไม่ตรงบัญชี (ข) เงินของสมาชิกเข้าถึงไม่ได้เพราะบั๊ก (ค) เหตุผิดนัดจริงที่ทำให้ความเสียหายที่คาดเกินเพดานที่ตกลง หรือกองทุนสำรอง+หลักประกันไม่พอตามแบบจำลองที่ใช้อยู่ (ง) ความเห็นกฎหมายออกมาไม่เป็นผลดี หรือกฎ stablecoin ใหม่กระทบ (จ) สัญญากลุ่มหรือที่อยู่ของสมาชิกถูก blocklist หรือมีเหตุขัดข้องของ Arc/USDC ที่กระทบการโอน

## 4. คำถามสำคัญที่เจ้าของโครงการต้องตัดสินใจ (7 ข้อ)

1. **โครงการนี้ดำเนินการในเขตอำนาจใด** (ที่ตั้งผู้พัฒนา ผู้ดูแล multisig ผู้จัด และกลุ่มสมาชิกเป้าหมาย) และใครคือ "ผู้จัด" ทางกฎหมาย? แพลตฟอร์มจะรับเงินค่าบริการหรือไม่
2. **ความเสียหายสูงสุดที่สมาชิกหนึ่งคนรับได้** คิดเป็นกี่ USDC หรือกี่เปอร์เซ็นต์ของรายได้ต่อเดือน (ข้อนี้กำหนด φ, D, ขนาดกลุ่ม และเพดานวงเงิน)
3. **กลุ่มเป้าหมายระยะทดลอง** คนที่รู้จักกันจริง (ชุมชน ที่ทำงาน สหกรณ์) หรือคนแปลกหน้า? (คนแปลกหน้าไม่ควรอยู่ใน MVP)
4. **ผู้ดูแลเลือกเป็น Minimal-admin แล้ว (ที่อยู่ `0x223c2D5Af8120cAb3c68b5587feC7c8649Ce9c15` กุญแจเดียว)** ต้องตัดสินว่าจะย้ายไปเป็น multisig เมื่อใด และใครเป็นผู้ไกล่เกลี่ยข้อพิพาทนอกเชน เมื่อสัญญาตัดสินได้เพียงว่า "จ่ายหรือไม่จ่าย"
5. **ช่องทางแปลงสกุลท้องถิ่น–USDC และใครรับความเสี่ยงค่าเงิน** ผู้ให้บริการใดที่ถูกต้องตามกฎหมายของเขตเป้าหมาย และสมาชิกรับความเสี่ยงค่าเงินเองหรือไม่
6. **การถือกุญแจกระเป๋า** ผู้ใช้ถือเอง (non-custodial) หรือผู้ให้บริการถือแทน (มีผลทางกฎหมายต่างกันมาก)
7. **ใครออกเงินกองทุนสำรองและค่าตรวจสอบสัญญา/กฎหมาย** รวมถึงงบสำหรับการตรวจความปลอดภัยและความเห็นกฎหมายก่อนนำร่องเงินจริง
