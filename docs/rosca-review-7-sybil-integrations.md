# ทบทวน On-chain ROSCA + Microfinance บน Arc (ส่วนที่ 7: เชื่อมต่อกับอะไรเพื่อลด Sybil)

วันที่ตรวจ: 22 พ.ย. 2026 ป้ายกำกับ [F] ข้อเท็จจริงที่ตรวจ [A] สมมติฐาน [P] ข้อเสนอ

> **อัปเดต:** เจ้าของโครงการเลือกใช้ Human Passport (human.tech) โดยกำหนดคะแนน **มากกว่า 20** ดูหัวข้อ 6 ซึ่งยึดแทนข้อเสนอ World ID ในหัวข้อ 2 ส่วนที่ขัดกัน

## 0. คำตอบสั้น

ได้ แต่ **ไม่มีตัวเชื่อมต่อใดกำจัด Sybil ได้หมด** ตัวที่ตรงที่สุดและมีหลักฐานว่าใช้กับ Arc ได้คือ **World ID (หลักฐานว่าเป็นมนุษย์ที่ไม่ซ้ำ)** ตัวอื่นเป็นตัวเสริมหรือใช้ไม่ได้บน Arc ในตอนนี้ ผลที่ได้จริงคือทำให้ "หนึ่งคน หนึ่งตำแหน่ง" และทำให้ประวัติผิดนัดตามตัวคนไป ไม่ใช่ทำให้ผู้ใช้เชื่อถือได้

## 2. แบบที่เสนอ: ชั้นป้องกัน Sybil แบบซ้อนกัน

| ชั้น | กลไก | ต้องพึ่งภายนอก | ระยะ |
|---|---|---|---|
| L0 | ต้นทุนเงิน: φ, D, ผู้ค้ำที่วางเงินจริง, ลายเซ็นรายชื่อ (V1), สายรู้จักกัน (ส่วนที่ 5–6) | ไม่ | MVP |
| L1 | **ใบรับรองมนุษย์ไม่ซ้ำ** (World ID หรือใบรับรอง KYC) ผ่านสัญญา `IdentityGate` | ใช่ | MVP บน testnet เป็นตัวเลือก; เงินจริงหลังตัดสินใจเขตอำนาจ |
| L2 | คัดกรองกระเป๋า (Chainalysis/Elliptic/TRM) ก่อนออกใบรับรอง และแจ้งเตือนกระเป๋าที่ได้เงินจากแหล่งเดียวกัน | ใช่ (นอกเชน) | หลังนำร่อง |

### 2.1 `IdentityGate` ทำอะไร [P]

1. `registerHuman(...)`: ตรวจหลักฐาน World ID 4.0 ผ่าน `verify(...)` ของ `WorldIDSatellite` โดยตั้ง **signal = ที่อยู่กระเป๋า + chainId + ที่อยู่ gate** เพื่อให้หลักฐานใช้กับกระเป๋าอื่นไม่ได้ (กันขโมยหลักฐานที่ส่งใน mempool) action เป็นข้อความตายตัวที่ reduce เป็น field ตามเอกสาร (`uint256(keccak256(bytes(action))) >> 8`) [F ตามเอกสาร World]
2. เก็บ `humanId = nullifier` ต่อกระเป๋า และห้าม nullifier ซ้ำ (หนึ่งคนหนึ่งกระเป๋าที่ใช้งาน)
3. กลุ่มที่เลือก `requireHuman` (ส่วนหนึ่งของ `termsHash` ที่สมาชิกเซ็น) รับสมาชิกเมื่อ `humanOf(wallet) ≠ 0` และ `humanId` นั้นยังไม่มีตำแหน่งในกลุ่ม
4. การผิดนัดบันทึกกับ `humanId` ไม่ใช่กระเป๋า ทำให้ "กระเป๋าใหม่หนีประวัติ" ไม่ได้
5. การย้ายกระเป๋าต้องทำผ่านกระบวนการ migrate (ส่วนที่ 3 หัวข้อ 6.6 และ V12) เพราะ action เดิมให้ nullifier เดิม การลงทะเบียนใหม่จึงถูกบล็อก
6. **ตรวจเฉพาะตอนเข้าร่วม** เส้นทางจ่ายเงิน ผิดนัด และเบิกเงินไม่เรียก World verifier เลย ถ้า verifier ถูกอัปเกรดหรือล่ม จะรับสมาชิกใหม่ไม่ได้ แต่กลุ่มที่เริ่มแล้วทำงานต่อได้

ทางเลือก KYC: สัญญาตรวจลายเซ็น EIP-712 ของผู้ออกใบรับรองที่ฝังเป็น `immutable` ใน factory (ไม่มีอำนาจแก้รายชื่อผู้ออก ถ้าจะเปลี่ยนต้อง deploy factory ใหม่ ตรงกับหลักผู้ดูแลน้อยที่สุด) เก็บเฉพาะ `personHash` (แฮชเกลือของเอกสาร) ไม่เก็บข้อมูลส่วนบุคคลบนเชน

### 2.2 ใช้ตัวตนเพื่ออะไรได้ และไม่ได้

| ทำได้ | ทำไม่ได้ |
|---|---|
| จำกัดหนึ่งคนหนึ่งตำแหน่งต่อกลุ่ม | ทำให้ผู้ใช้ไม่ผิดนัด |
| ผูกประวัติผิดนัดกับตัวคน | ทราบรายได้ หนี้อื่น หรือความสามารถชำระ |
| จำกัดจำนวนกลุ่มที่ค้างพร้อมกันต่อคน | ห้ามการให้ยืม/ขายตัวตน (เช่นคนจริงยอมให้อีกคนใช้ใบรับรองของตน) |
| ใช้เป็นเงื่อนไข "คิวต้นรอบเฉพาะมนุษย์ที่ยืนยันแล้ว" | ป้องกันคนจริงหลายคนสมรู้กัน |

**ข้อควรระวังทางเศรษฐศาสตร์**: ถ้ากำไรจากการหนี (ส่วนไม่มีหลักประกัน เช่น 350 USDC ในตัวอย่าง) สูงกว่าราคาที่คนจะเช่า/ขายตัวตนที่ยืนยันแล้ว การโจมตียังคุ้ม ดังนั้น **ตัวตนต้องไม่ใช้ลด φ ต่ำกว่าสูตรในส่วนที่ 5 หัวข้อ 1** ใช้เสริมเท่านั้น (สอดคล้องส่วนที่ 3 หัวข้อ 5)

## 3. ความเสี่ยงและต้นทุนของการเชื่อม

| ประเด็น | ผล |
|---|---|
| การกันผู้ใช้ออก | ผู้ที่ไม่มีโอกาสยืนยัน (ที่ตั้ง อุปกรณ์ เอกสาร) เข้าร่วมกลุ่มที่บังคับยืนยันไม่ได้ ซึ่งขัดกับกลุ่มเป้าหมายที่เข้าถึงบริการการเงินได้จำกัด จึงควรให้เป็น "ตัวเลือกต่อกลุ่ม" ไม่ใช่เงื่อนไขทุกกลุ่ม |
| ความเป็นส่วนตัว | nullifier เป็นสาธารณะ เชื่อมกระเป๋ากับตัวตนแบบนิรนามข้ามทุกกลุ่มของเรา คนที่รู้ว่ากระเป๋านั้นเป็นใครก็เห็นประวัติกลุ่มได้ ต้องแจ้งผู้ใช้ก่อนยืนยัน |
| การพึ่งผู้ให้บริการ | World ควบคุมตัว verifier (เอกสารให้อยู่หลัง proxy ที่อัปเกรดได้ และแนะนำให้สัญญาผู้ใช้อัปเกรดได้ตามเวอร์ชัน) ผมเลือกโครงที่ตรวจเฉพาะตอนเข้าร่วม และไม่ทำให้ gate อัปเกรดได้เพื่อไม่เพิ่มสิทธิ admin ถ้า World เปลี่ยนอินเทอร์เฟซ การรับสมาชิกใหม่ต้องใช้ gate รุ่นใหม่ผ่าน factory ใหม่ |
| กฎหมาย | ข้อมูลชีวมิติ/เอกสารมีข้อกำหนดเฉพาะเขตอำนาจ ผมไม่ทราบเขตอำนาจ จึงไม่ได้ตรวจ ต้องให้ทนายประเมินก่อนบังคับใช้ (ส่วนที่ 4 หัวข้อ 2) |
| ต้นทุน | ค่า gas ของ `verify` บน Arc และค่าบริการผู้ให้บริการ KYC/คัดกรองยังไม่ได้วัด |
| การทดสอบ | ยืนยันไม่ได้ว่า Arc Testnet ตรวจหลักฐาน sandbox ได้ ต้องทดลองกับ World ID sandbox ก่อน และเขียนทดสอบอัตโนมัติด้วย verifier จำลองที่ implement อินเทอร์เฟซเดียวกัน |

## 4. สิ่งที่ต้องตัดสินใจก่อนเขียนโค้ดส่วนนี้

1. เขตอำนาจที่ดำเนินการ (กำหนดว่า World ID/KYC ใช้ได้และถูกกฎหมายหรือไม่)
2. จะให้การยืนยันตัวตน "บังคับ" "ตัวเลือกต่อกลุ่ม" หรือ "ไม่ใช้ใน MVP" (ผมแนะนำตัวเลือกต่อกลุ่ม)
3. ยอมรับผู้ให้บริการที่ต้องพึ่ง (World หรือผู้ออกใบรับรอง KYC ที่เลือกเอง) หรือไม่

## 5. การเปลี่ยนแปลงสเปกที่เสนอ

- เพิ่มอินเทอร์เฟซ `IIdentityGate` ใน `RoscaGroup` (ไม่บังคับ ปิดไว้เป็นค่าเริ่มต้น)
- เพิ่ม `requireHuman` และที่อยู่ gate ลงใน `termsHash` (V1)
- เพิ่ม invariant: `humanId` หนึ่งค่ามีตำแหน่งได้ไม่เกินหนึ่งตำแหน่งต่อกลุ่ม และเส้นทางจ่าย/ผิดนัดไม่เรียกสัญญาภายนอกนอกจาก USDC
- เพิ่มทดสอบ: ใช้หลักฐานเดียวกันกับกระเป๋าอื่นต้อง revert; ใช้ nullifier ซ้ำต้อง revert; verifier ล่มแล้วกลุ่มที่เริ่มแล้วจ่าย/ผิดนัดได้ตามปกติ

## 6. การตัดสินใจ: ใช้ Human Passport (human.tech) คะแนน > 20

ข้อเท็จจริงที่ตรวจ [F, docs.passport.human.tech: Stamps API v2 reference อัปเดต 3 ก.พ. 2026 และหน้า Scoring thresholds]:
- ขอคะแนนได้ที่ `GET https://api.passport.xyz/v2/stamps/{scorer_id}/score/{address}` ต้องมี API key (ส่วนหัว `X-API-KEY`) และ Scorer ID จาก developer.passport.xyz ผลลัพธ์มี `score`, `passing_score`, `threshold`, `expiration_timestamp` และรายการ stamp
- เกณฑ์แนะนำของ Passport คือ 20 และ `passing_score` หมายถึงคะแนน **เกิน** เกณฑ์ ตรงกับ "มากกว่า 20" ที่เลือก
- เอกสารระบุตัวเองว่า "ไม่ใช่ระบบสมบูรณ์ ไม่ใช่ Sybil ทุกรายจะถูกกำจัดที่เกณฑ์นั้น" และระบุเกณฑ์ 20 / 25 / 30 ว่ากัน Sybil ได้ "มีประสิทธิภาพ / มากขึ้น / มากที่สุด" แลกกับความเสี่ยงที่ผู้ใช้จริงผ่านไม่ได้ "ต่ำ / ปานกลาง / สูง"
- โครงสร้างบนเชนของ Passport ไม่มี Arc (ตัวถอดรหัสมีบน Arbitrum, Base, Linea, Optimism, Scroll, Shape, ZkSync) [F] จึงต้องใช้เส้นทาง "ผู้รับรองนอกเชน"
- ขีดจำกัดอัตราเริ่มต้น Tier 1 = 125 คำขอต่อ 15 นาที, timeout 60 วินาที [F]

### 6.1 สถาปัตยกรรม [P]

1. ผู้ใช้เปิดหน้าเว็บ เซ็นข้อความพิสูจน์ว่าคุมกระเป๋า (ข้อความมีที่อยู่ กลุ่ม เวลา และ nonce) เพราะ **คะแนนของที่อยู่ใดก็ขอได้โดยไม่ต้องเป็นเจ้าของ** ถ้าไม่พิสูจน์ ใครก็เอาคะแนนสูงของคนอื่นมาใช้ได้
2. บริการ `PassportAttestor` (แบ็กเอนด์ที่เราดูแล) ตรวจลายเซ็น เรียก Stamps API ด้วยคีย์ลับ ฝั่งเซิร์ฟเวอร์เท่านั้น แล้วแปลงคะแนนเป็นจำนวนเต็ม (หน่วย 0.001) โดยแยกสตริง **ไม่ใช้ float**
3. ถ้า `score > 20` และ `expiration_timestamp` ยังไม่หมด บริการเซ็น EIP-712 `HumanAttestation { wallet, scoreMilli, expiresAt, nonce, chainId, gate, termsHash }` สั้นอายุ [A: 24 ชม.] เพื่อให้ขายต่อหรือเช่าได้ยากขึ้น
4. ผู้ใช้ส่งใบรับรองเข้า `join(...)` ของกลุ่ม สัญญาตรวจ: ผู้เซ็น = `attester` ที่ฝังเป็น immutable; `wallet == msg.sender`; `chainId`, `gate`, `termsHash` ตรง; ยังไม่หมดอายุ; nonce ยังไม่ใช้; **`scoreMilli > MIN_SCORE_MILLI` ตรวจซ้ำในสัญญา** เพื่อให้ผู้รับรองลดเกณฑ์เงียบ ๆ ไม่ได้
5. `minScoreMilli` (ค่าเริ่มต้น 20,000) เป็นส่วนหนึ่งของ `termsHash` ที่สมาชิกเซ็น (V1) กลุ่มตั้งสูงกว่านี้ได้ (เช่น 25,000) ลดไม่ได้ต่ำกว่า 20,000
6. ตรวจเฉพาะตอนเข้าร่วม การจ่าย ผิดนัด และเบิกเงินไม่พึ่งผู้รับรองหรือ Passport เลย ถ้า API ล่มหรือเปลี่ยนโมเดลคะแนน จะรับสมาชิกใหม่ไม่ได้ แต่กลุ่มที่เริ่มแล้วทำงานต่อได้

### 6.2 ใครต้องผ่านเกณฑ์: ตามความเสี่ยงของตำแหน่ง ไม่ใช่ทุกคน [P]

ผู้ใช้เป้าหมายที่ไม่เคยใช้คริปโตอาจไม่มี stamp พอให้ถึง 20 (ข้อนี้เป็นสมมติฐาน [A] ที่ต้องทดสอบกับผู้ใช้จริง เพราะเอกสาร Passport ประเมินความเสี่ยงต่อผู้ใช้จริงจากกลุ่มผู้ใช้ทั่วไป) จึงบังคับเฉพาะตำแหน่งที่ส่วนไม่มีหลักประกันสูง

ส่วนไม่มีหลักประกันของตำแหน่ง k = (1 − φ) × C × (N − k) − D ตัวอย่าง N = 10, C = 100, φ = 50%, D = 100 [คำนวณ]:

| ตำแหน่ง k | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 ถึง 10 |
|---|---|---|---|---|---|---|---|---|
| ส่วนไม่มีหลักประกัน (USDC) | 350 | 300 | 250 | 200 | 150 | 100 | 50 | 0 |

กติกา: ตำแหน่งที่ส่วนไม่มีหลักประกัน **มากกว่าเพดาน E** ต้องมีใบรับรองคะแนน > 20 ถ้าตั้ง E = 100 [A เพดานของตัวอย่าง ต้องมาจากเพดานความเสียหายที่เจ้าของโครงการตกลง] ตำแหน่ง 1 ถึง 5 ต้องผ่าน ตำแหน่ง 6 ถึง 10 ไม่ต้อง ผู้ที่ไม่มีคะแนนจึงยังเข้าวงออมได้ในตำแหน่งท้ายที่เสี่ยงต่ำ ค่า E เป็นส่วนของ `termsHash`

### 6.3 สิ่งที่ Passport ให้ไม่ได้ (ต่างจาก World ID)

| ประเด็น | ผล | ที่ต้องทำ |
|---|---|---|
| **ไม่มี ID ผูกตัวคนข้ามกระเป๋า** คะแนนเป็นของที่อยู่ ไม่ใช่รหัสบุคคล | ประวัติผิดนัดผูกกับที่อยู่ ผู้ผิดนัดสร้างที่อยู่ใหม่แล้วสะสม stamp ใหม่ได้ ต้องเสียเวลาและบัญชีใหม่ แต่ไม่มีการบังคับเชิงเข้ารหัส | ใช้ค่าใช้จ่ายและเวลาเป็นกำแพง เก็บบัญชีขึ้นบัญชีดำตามที่อยู่ และไม่ลด φ ตามคะแนน |
| ปั่นคะแนนได้ด้วยบัญชีจริงหลายชุด ซื้อบัญชีที่มีคะแนน หรือเช่าที่อยู่ | Sybil ที่ลงทุนยังผ่าน Passport มีการ dedup stamp ข้ามที่อยู่ ซึ่งทำให้บัญชีเดียวใช้กับหลายที่อยู่ไม่ได้ [F ฟิลด์ `dedup`] แต่ปิดช่องไม่ได้ทั้งหมด | ผูกกับเศรษฐศาสตร์: กำไรจากการหนี (ส่วนไม่มีหลักประกัน) ต้องไม่เกินต้นทุนปั่นคะแนน ซึ่งผมไม่มีข้อมูลต้นทุนจริง |
| คะแนนเปลี่ยนตามเวลาและตามน้ำหนักที่ Passport กำหนด (stamp หมดอายุ ตัวคูณปรับ) | ที่อยู่ที่ผ่านวันนี้อาจไม่ผ่านพรุ่งนี้ และกลับกัน | ตรวจ ณ ตอนเข้าร่วมเท่านั้น ไม่ผูกสิทธิหลังเข้าร่วมกับคะแนน; บันทึกคะแนนและเวลาในเหตุการณ์เพื่อตรวจย้อนหลัง |
| ผู้ใช้เปราะบางผ่านไม่ได้ | กันผู้ใช้เป้าหมายออก | กติกา 6.2 + ทดลองกับผู้ใช้จริงก่อนกำหนดเพดาน E |
| ความเป็นส่วนตัว | แบ็กเอนด์ของเรามองเห็นรายการ stamp ที่ผู้ใช้เชื่อม (เช่นบัญชีสังคมใดบ้าง) และการเชื่อมที่อยู่กับ "ผ่าน/ไม่ผ่าน" เป็นสาธารณะบนเชน | เก็บเฉพาะคะแนนและเวลา ไม่บันทึกรายการ stamp; แจ้งผู้ใช้ก่อนเซ็น; เขตอำนาจที่ไม่ทราบทำให้ยังไม่ได้ตรวจภาระกฎหมาย |
| ต้องพึ่งผู้ให้บริการ | Passport เปลี่ยนเงื่อนไข API ค่าบริการ หรือหยุดบริการได้; ขีดจำกัด Tier 1 อาจไม่พอเมื่อมีผู้ใช้มาก (ผมไม่ทราบเงื่อนไขการใช้งานเชิงพาณิชย์) | แคชผล; ตรวจเงื่อนไขการใช้ก่อนใช้จริง; ออกแบบให้สลับผู้รับรองได้โดย deploy factory ใหม่ |

### 6.4 ความเสี่ยงใหม่ที่การเชื่อมนี้เพิ่ม และวิธีแก้

| # | ความเสี่ยง | วิธีแก้ |
|---|---|---|
| P1 | **กุญแจผู้รับรองถูกขโมย** ผู้โจมตีออกใบรับรองให้กระเป๋า Sybil ได้ไม่จำกัด (กองทุนไม่เสียหายโดยตรง แต่การป้องกัน Sybil หายไป) | กุญแจผู้รับรอง **ต้องไม่ใช่ที่อยู่ผู้ดูแล** (`0x223c…9c15`) เก็บเป็นความลับฝั่งเซิร์ฟเวอร์ อายุใบรับรองสั้น จำกัดอัตราออกใบ บันทึกทุกใบ เปลี่ยนคีย์ = factory ใหม่ ความเสียหายจากกุญแจรั่วจำกัดที่กลุ่มใหม่ที่เปิดหลังรั่ว |
| P2 | ผู้โจมตีขอใบรับรองให้ที่อยู่ของคนอื่นที่คะแนนสูง | ต้องมีลายเซ็นพิสูจน์การคุมกระเป๋าก่อนเรียก API และสัญญาตรวจ `wallet == msg.sender` |
| P3 | ใบรับรองถูกใช้ซ้ำหรือข้ามกลุ่ม/ข้ามเชน | EIP-712 ผูก `chainId`, `gate`, `termsHash`, `nonce` เก็บ nonce ที่ใช้แล้ว |
| P4 | กระเป๋าแบบสัญญา (เช่น Circle modular wallet) ลายเซ็นพิสูจน์ต้องเป็น ERC-1271 และ Passport ให้คะแนนที่อยู่สัญญาได้หรือไม่ยังไม่ทราบ [A] | ทดสอบกับกระเป๋าที่จะใช้จริงก่อน ถ้าไม่ได้ ให้ใช้ EOA สำหรับตำแหน่งที่ต้องผ่านเกณฑ์ |
| P5 | ผู้รับรองออกใบให้เกินเกณฑ์ที่ตกลง | สัญญาตรวจ `scoreMilli > minScoreMilli` ซ้ำเอง (ข้อ 6.1 ข้อ 4) |
| P6 | API ล่มช่วงรับสมาชิก ทำให้กลุ่มค้างใน Recruiting | มีเส้นตายรับสมัครและยกเลิกแล้วคืนเงิน (V13) |

### 6.5 ข้อมูลลับและสิ่งที่ผมต้องการจากคุณก่อนเขียนโค้ดส่วนนี้

- คุณต้องสร้างบัญชีที่ developer.passport.xyz เพื่อได้ **Stamps API key** และ **Scorer ID** (ตั้งเกณฑ์ที่ Scorer ได้ 20) **อย่าวางคีย์ในแชท** ให้เพิ่มลง `.env` ผ่านแผนผังไฟล์ในชื่อ `PASSPORT_API_KEY` และ `PASSPORT_SCORER_ID` แล้วบอกผม
- ต้องมีกุญแจผู้รับรองคนละใบกับกุญแจผู้ดูแล บน testnet ผมสร้างที่อยู่สำหรับทดสอบได้ แต่คุณควรเก็บกุญแจจริงเอง
- การทดสอบอัตโนมัติจะใช้ข้อมูลจำลองของ API และผู้รับรองจำลอง ไม่เรียก API จริง ผมจะทดสอบกับ API จริงได้เมื่อมีคีย์เท่านั้น

### 6.6 การเปลี่ยนแปลงสเปกที่ตามมา

- แทน `IdentityGate` (World ID) ด้วย `PassportGate` ที่ตรวจ EIP-712 จากผู้รับรอง (อินเทอร์เฟซ `IIdentityGate` เดิมยังใช้ได้ เพื่อสลับกับ World ID ในอนาคตโดย factory ใหม่)
- เพิ่ม `minScoreMilli` และ `maxUngatedExposure E` ลงใน `termsHash`
- ตัดสิ่งที่พึ่ง `humanId` ออก (ไม่มีใน Passport): ประวัติผิดนัดผูกกับที่อยู่
- เพิ่ม invariant: ตำแหน่งที่ส่วนไม่มีหลักประกันเกิน E ต้องมีใบรับรองที่ถูกต้อง ณ ตอนเข้าร่วม; ใบรับรองใช้ได้หนึ่งครั้ง; การจ่าย/ผิดนัด/เบิกไม่เรียกผู้รับรอง
- เพิ่มทดสอบ: คะแนนเท่ากับ 20.000 ต้องไม่ผ่าน (ต้องมากกว่า); ใบรับรองหมดอายุ ใช้ข้ามกลุ่ม ใช้ซ้ำ หรือเซ็นโดยคีย์อื่น ต้อง revert

> **แก้ไขจากการตรวจรอบสอง (ส่วนที่ 8):** ข้อ 6.2 เพดาน E ใช้เป็นเพดานรวมของทุกตำแหน่งที่ไม่มีใบรับรอง (W1) ผู้แทนต้องมีใบรับรอง (W2) ลำดับขั้น `termsHash` → ใบรับรอง → `accept` ต้องเป็นไปตาม W5 ผู้รับรองต้องตรวจสถานะบนเชนก่อนเซ็น (W6) และแปลงคะแนนตาม W7 ห้ามใช้ `passing_score`
